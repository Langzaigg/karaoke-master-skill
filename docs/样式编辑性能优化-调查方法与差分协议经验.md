# 样式编辑性能优化——调查方法与差分协议经验

> 2026-10，「用户反馈改色卡顿（机器好）」调查与三项优化的完整经验沉淀。
> 目标读者：后续要优化**改布局 / 改特效 / 改字体**等交互延迟的人。
> 分支：`perf/style-edit-pipeline`（P1/P2 已完成并验证；P3 差分协议代码

## 1. 结论速览

改色停手后的完整时间线（4K 实际工程，优化前实测）：

| 时刻 | 步骤 | 线程 | 优化前 | 优化后 |
|---|---|---|---|---|
| +0ms | 面板提交 → `_apply_style` | GUI | 2.6ms/tick | 不变 |
| +220ms | 预览防抖到期，派发 worker 重配 | GUI 0.05ms | — | — |
| +222~374ms | worker 重配：IR 重序列化 ~52ms + sidecar JSON 解析/场景重建 ~85ms + D2D ~5ms | 后台 | ~152ms | P3 目标 ~10-40ms（待启用） |
| +250ms | 歌词表色点刷新（98 行 × 5 列重写 + 整视口重绘） | **GUI** | **37~50ms** | P1 后 <5ms |
| +386ms | 首帧到达，预览出新颜色 | GUI 0.16ms | 端到端 ~0.39s | ~0.29s（P1+P2） |
| +1500ms | 偏好落盘（2 次整读 + 2 次旧路径修复全树遍历） | **GUI** | **32~72ms** | P2 后 ~9ms |

用户说「改完色卡」的元凶就是两个落在 GUI 线程上的**延时炸弹**：+250ms 的
整表刷新和 +1.5s 的偏好落盘——都和「机器好」无关（前者是控件数据量，
后者是纯 Python 串行遍历）。

## 2. 调查方法论（可复用）

这次定位花时间的地方不是「看代码」，而是**建立可信的测量**。以下手段
按性价比排序，均可复用：

1. **黄金标准：真实工程 + 真实控件离屏实例化**。直接构造
   `SubtitleRenderWindow(embedded=True)` + `_open_project_path(真实.yurika)`，
   再整体计时 `_apply_style` / `_apply_preview_style_now`。能覆盖所有你
   没想到的杂项；离屏跑不了真重绘（数据段可信，重绘成本要换算，见 3）。
2. **GUI 心跳探针**：10ms `QTimer` 记录最大触发间隔，挂在整个停手窗口
   （4 秒）上。这次抓到偏好落盘的 39ms 峰值就是靠它对上的。
3. **时间线打点**：钩住关键函数（防抖回调 / worker 进度信号 / frame_ready /
   落盘），输出相对最后操作的毫秒时间线，一眼看出「哪个延迟后跟哪个成本」。
4. **cProfile 批量 tick**：120 次真实 `_set_color` 后看累计榜，区分
   「每 tick 都付」（面板回灌 / 撤销序列化）与「停手后付一次」。
5. **分解验证 > 假设**：这次「GIL 争用」假设就是被 A/B 对照（worker 忙/
   空闲两种状态下测同一调用）排除的——p50 3.27 vs 3.65ms，无争用。
6. **口径意识**：离屏 = 数据段；屏幕 = 数据 + 栅格化（代码注释里的
   「37ms 含重绘」就是屏幕口径的基准）。两套数字都要记，别混。

测量脚本（%TEMP%，可直接改造复用）：`measure_color_timeline.py`（时间线+
心跳+播放冻结）、`measure_gui_thread_steps2.py`（控件级分段）、
`profile_color_edit.py`（tick 级 cProfile）、`measure_apply_style_full.py`
（主窗口整函数）、`measure_p3_patch.py`（差分协议对照）。

## 3. 已完成的优化与可复用模式

### P1 · 歌词表色点窄刷新（4.85ms → 0.4ms 数据段，屏幕整视口重绘消失）

**模式：签名分类 + 只碰真正变化的列。** `LyricsList.set_style` 本来就有
三档签名（布局/色点/动画）分流，但色点档复用了整表 `_refresh_presentation`
（98 行 × 5 列全重写）。改成只重画角色列图标，取色口径提取成
`_role_swatch_icon_for` 供整表/窄表两路共用（单一事实源，防漂移）。

**复用提示**：改特效摘要列、改布局列名同理——先查签名档位，再让窄刷新
只落在一列。Qt 侧脏区自动收敛到该列的矩形，重绘成本随脏区走。

### P2 · 偏好落盘瘦身（32~72ms → 9ms）

**模式：消除冗余读 + 按内容付费。** 三个正交手段：
- **(mtime, size) 键控原文缓存**：自己写盘后缓存刷新为写入内容；外部实例
  改盘由 stat 变化自然失效。多开三方合并语义原样保留。
- **文本闸门 + 逐内容判定**：改名迁移自愈的全树遍历，文本里连一个已知
  应用目录名都没有时一次不跑；跑过且无事可修的同一份内容不再重跑。
- **命名空间级写** `write_app_settings_namespace`：桥保存不再整读整写，
  等价于旧「load→只改本段→save(merge=False)」链路（那次 load 的基线就是
  盘上内容），额外收益是未知键不再被丢弃。

**复用提示**：任何「防抖后全量落盘」的路径都值得查三件事——读了几次盘、
有没有每次都跑的遍历、能不能只写变化的那一段。

### P3 · GPU 预览 `gpu_configure_style` 差分协议（代码就绪，默认关闭）

见 §5。

## 4. 改样式热路径地图（背景知识，优化前口径）

- **每 tick（调节中）**：面板 `_update_style`（含 `_sync_subtitle_scheme_controls`
  回灌 ~1.2ms）+ 主窗口 `_apply_style`（类型判定 0.26 / 撤销序列化 0.54 /
  面板等值快路径 0.2ms）≈ 2.6ms，不卡。220ms 纯尾沿防抖保证连调期间零重渲。
- **停手 220ms 后**：worker `configure_gpu` = `build_render_ir`（paint scope
  命中布局缓存仍要**全量重序列化** 1.47MB，~52ms）+ sidecar `configure`
  （Qt JSON 解析 + RenderConfig 重建，~85ms）+ `gpu_configure`（D2D 场景，
  资源缓存热时 ~5ms）。
- **播放中改色**：configure 窗口内无帧交付 → 字幕层冻结 ~170ms（视频画面
  不受影响），220ms 后开始。好 GPU 帮不上，这 170ms 是 CPU 侧成本。
- 每字 IR **不含颜色**（颜色在 style 段，C++ 按 role→方案解析）；但
  **行级数据嵌有样式派生内容**：动画档位、信号旗标、`fx_bursts`（粒子
  规划，内嵌逐字解析色的实色回退 + paint 规格）——见 §5.2 的教训。

## 5. P3 差分协议：设计、教训与现状

### 5.1 设计（正确性优先的三道闸门）

1. **资格闸门（Python）**：`style_patch_base_key` = (画面参数, 逐源
   `value_signature(track)`, `lyric_layout_style_signature(style)`)。key 相等
   ⇔ 行数据与上一次全量 configure 同源。任何不匹配自动走全量，无中间态。
2. **重放语义（C++）**：样式段在**全新默认构造的 RenderConfig** 上重放
   （键缺席→默认值，与全量解析逐字节同义），行数据派生字段（lines/rubies/
   矢量符号表/主轨偏移）从旧 config 搬运——避免「patch 到既有对象上、
   缺省键沿用旧值」这一类语义漂移。
3. **行级样式差分**：`lines_style` 载荷按 (source_index, source_line_index)
   一一对齐合并（行数/键不符按漂移拒绝）；解析侧提取 `applyLineStyleSection`
   供全量解析与差分合并共用同一份代码。

协议：`gpu_configure_style` 命令（`json_protocol` / `command_router` /
`gpu_lifecycle_commands` / `backend.configure_style_gpu` /
`render_ir.build_style_patch_ir` / `protocol.lines_style_to_ir`）。sidecar
收到后在既有行数据上重放 style/titles/fx_sprites/lines_style 段，再走
现有 `gpu_configure` 尾段（含 glow/文本层/布局三张缓存清账——**与全量
`configure` 命令同口径**，这是第一次实测分歧时抓到的坑）。

### 5.2 两个关键教训

- **「每字 IR 不含颜色」≠「行数据与颜色无关」**。`fx_bursts` 无条件内嵌
  逐字解析色的实色回退（`plan_line_bursts` 的 `_cached_particle_solid`），
  纯改色也会改变行数据。最初的「只发 style 段」设计因此不成立，必须带
  `lines_style` 差分。**任何差分协议都要先枚举「嵌在行数据里的样式派生
  字段」**——动画档位、信号旗标、粒子、（未来新增的行级装饰）。
- **帧 checksum 不是重工程的合法 oracle**。glow+粒子+角色的真实工程上，
  「重配后首帧」本身有漂移（全量 vs 全量 1000px 级、patch vs 全量 3700px
  级，幅度同为 mean≈7/255 的亮度级；同配置内复渲则逐字节一致）。简单
  工程（无 glow/粒子活动）patch 与全量**逐字节等价**（金标准测试通过）。
  判定等价要选确定性的场景，或用容差 + 与「全量自身噪声底」对比。

### 5.3 现状与启用条件

- 测试：`tests/test_subtitle_render_gpu_style_patch.py`——段等价、行级
  字段零漂移、闸门 key、端到端 checksum 金标准（无 exe 自动 skip）。
- 性能（真实工程实测）：全量 configure ~172ms → patch ~110-120ms。
  不如预期的 10-20ms：剩余大头是 Python 侧 `lines_style` 的 bursts 规划
  （66 行 × 逐字 char_styles 解析）。后续方向：fx 字段未变时按签名复用
  上一版 bursts；或把 bursts 的 paint 规格缓存按 (样式, 角色) 命中。
- **默认关闭**（`KROK_SUBTITLE_GPU_STYLE_PATCH=1` 显式开启）。启用前置
  条件：在主干用 GPU-Painter corpus 对照 + 重工程容差基准查清 §5.2 的
  首帧漂移根因（怀疑 realization/场景重建的首次渲染路径），并把剩余
  Python 成本压到 30ms 内。

## 6. 复用到改布局 / 改特效的指引

| 场景 | 与改色的差异 | 可套用的资产 |
|---|---|---|
| 改字号/边距/行数等布局参数 | 布局签名变化 → 全量 configure 必要（几何真变了）；缩容还会同步重排页面（GUI ~100ms，含双份全轨深拷贝入撤销栈） | 布局计划缓存已按签名复用（重排计算 ~3ms 热度量）；若要再压，用 P3 同款差分思路做「lines-only patch」（位置数组比 style 段更小） |
| 改出入场/唱字动画档位 | 已归入 `anim_lightweight` → paint scope；动画类型字段还触发歌词表「特效」列的**立即整表刷新**（~5ms 数据段，同 P1 手法可窄化） | P3 patch 直接覆盖（行级动画字段在 lines_style 里） |
| 改扫字线/指示灯/音量柱参数 | 纯 style 段，不嵌行数据 | P3 patch 的最小受益集 |
| 改粒子参数 | `fx_bursts` 嵌行数据（count/size/颜色模式/动画时长缩放） | P3 lines_style 已覆盖；性能上 bursts 规划是下一个优化点 |
| 任何「停手后 N ms 落盘/刷新」 | — | §2 心跳探针 + §3 P2 三件套 |

## 7. 防护清单（下次改交互路径时过一遍）

1. 每 tick 成本 <5ms？停手后的每一笔延迟都在哪个时刻、哪个线程？
2. 防抖是纯尾沿还是首沿+尾沿？连续操作期间是否真的零成本？
3. 落盘类路径读了几次盘？有没有每次都跑的全树遍历？
4. 后台任务真的在后台？（这次验证过 GPU worker 不饿 GUI——但要用
   A/B 对照验证，不要凭直觉。）
5. 差分类优化：闸门是什么？闸门失效时如何自动回落全量？
6. 行/字数据里嵌了哪些样式派生字段？（差分协议的第一正确性问题。）
7. 验证 oracle 是确定性的吗？（帧 checksum 在 glow/粒子工程上不合法。）
8. 动 native 共享头文件 → `--clean-first` 全量重建（AGENTS §8.11）；
   Windows 下从 Git Bash 构建 native 要过 `VsDevCmd.bat`（临时 bat 包装
   最稳）；构建前杀残留 `krok_subtitle_renderer.exe`（LNK1104）。
